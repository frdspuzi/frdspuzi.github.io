# Design System — frdspuzi.github.io

This site now has a CSS custom-property (token) layer, defined once in `assets/styles.scss` and consumed via `var(--token-name)` everywhere else. Reuse the tokens below instead of hardcoding a new hex value; if you introduce a genuinely new value, add it as a token there and document it here.

## Foundation: GitHub Primer
The base is [Primer](https://styleguide.github.com/primer/), self-hosted as `assets/vendor/primer.css` (pinned to v11.0.0, linked in `header.html` — see `.ai/architecture.md` for why this moved off a live unpkg.com `@import` on 2026-08-03). Layout, type scale, and most spacing come from Primer utility classes (`f1`–`f6`, `d-flex`, `p-3`/`p-4`/`p-5`, `mb-4`/`mb-5`/`mb-6`, `Box`, `box-shadow-small/medium/large`, `rounded-1`/`rounded-2`, `btn`, `flash`, etc.) — reach for a Primer class first before writing new CSS. **`primer.css` was PurgeCSS'd down to only the ~119 classes actually used site-wide on 2026-08-04** (144,991 bytes → ~18,000, PageSpeed had flagged 22.5 KiB of it as unused) — see the file's own header comment for the full rationale, the safelist, and how to re-run the purge after adding a Primer class no page currently uses. Practical effect: **a Primer class not already used somewhere on the live site won't have any styling until the purge is re-run** — check the vendored file directly (`grep '\.your-class' assets/vendor/primer.css`) before assuming a Primer utility "just works."

Every token value below is, not coincidentally, one of **GitHub's own Primer light/dark primitives**.

## Color

**Dark mode is a real runtime toggle now**, not just a build-time setting. A `data-theme="light"|"dark"` attribute on `<html>` picks the theme; both themes' full token values ship to the browser on every page load via a `:root { }` block (light defaults) and a `[data-theme="dark"] { }` override block in `assets/styles.scss`:
```scss
:root { --fg: #24292e; /* ... */ }
[data-theme="dark"] { --fg: #c9d1d9; /* ... */ }
```
`_config.yml`'s `style: light|dark` still matters — Liquid uses it to set the *initial* `data-theme` value at build time (`_includes/header.html`: `<html data-theme="{{ site.style }}">`) — but it's now just the default a first-time visitor sees, not the only theme that exists. The Rectangle toggle button (`_includes/floating_toc.html`, see Component Patterns) flips `data-theme` at runtime and persists the choice to `localStorage`; a small synchronous inline script early in `<head>` reads that stored preference before first paint, so returning visitors don't see a flash of the build-time default.

**Also new:** `.theme-fg`, `.theme-fg-muted`, `.theme-surface`, `.theme-surface-page`, `.theme-border` utility classes in `assets/styles.scss` — these replace what used to be per-element `{% if site.style == 'dark' %}bg-gray-dark{% else %}bg-white{% endif %}`-style Primer class toggles across `_layouts/*.html`, `masthead.html`, `interests.html`, `projects.html`, `learning_board.html`, `repo-card.html`, `post-card.html`, `topic-card.html`. **There are no `{% if site.style == 'dark' %}` branches left anywhere in the codebase** — every one was converted to a token or a `.theme-*` class specifically so the runtime toggle actually works everywhere, not just in the sections that already used tokens. `.yt-flash` (`youtube_feed.html` only) is the one scoped one-off — its dark-mode background was a translucent white tint, not a plain color swap, so it's a `[data-theme="dark"] .yt-flash { }` override rather than a token.

**Dark surfaces are deliberately near-black, not GitHub's dark theme.** The dark values above (`--surface: #121212`, `--surface-alt: #0a0a0a`, `--surface-page: #1e1e1e`, `--surface-raised: #1a1a1a`, `--border: #2a2a2a`) are a Material-dark-inspired neutral palette, chosen explicitly over GitHub's own (blue-tinted, less dark) `#161b22`/`#0d1117`/`#2f363d`/`#24292e`/`#444d56` — a deliberate "IDE dark mode, darker" request, not a drift-fix. The elevation order is preserved (`surface-alt` darkest → `surface` → `surface-raised` → `surface-page` lightest), just compressed toward black. `--fg`/`--fg-muted`/`--accent`* were left unchanged — they already read fine against the darker backgrounds.

**Dark-mode contrast was checked by computing WCAG ratios directly, not by eyeballing.** One real failure found: making `--success-bg` a flat `#34d058` in dark mode (during the earlier full-site-wide pass) put `--success-fg` (`#7ee787`) text on it at **1.3:1** contrast — both are similarly-bright greens, nearly unreadable. Fixed by making dark mode's `--success-bg` translucent (`rgba(46,160,67,0.15)`, composited over whatever surface sits behind it) instead of solid — restores ~10:1 contrast, and happens to be closer to what this box used before the earlier token pass flattened it to a plain hex. Light mode's `#dcffe4`/`#176f2c` pairing was already fine (~5.8:1) and is untouched. Every other themed text/background pairing was checked the same way and clears WCAG AA (4.5:1) comfortably — `--fg`/`--fg-muted`/`--accent` all sit at 6:1–12:1 against every dark surface token.

**Primer's own stock classes needed dark-mode overrides too.** `.btn`, `.btn-outline`, `.btn-invisible`, `.text-gray`, `.text-gray-light`, `.text-gray-dark`, `.link-gray`, `.Box`, `.form-control`, and `.border`/`.border-top` all have fixed light-mode-only colors baked into the imported Primer CDN bundle — they were never touched by the token conversion because they're Primer's classes, not per-element Liquid branches. Found by actually clicking the toggle and spotting things that stayed light: buttons (gratitude's "AI Suggestion"/"Clear", the Medium "Get updates" button, trivia's prev/next arrows and "Read full article" link, trivia answer options), the `.Box`-based article cards in `thoughts.html`, and the gratitude textarea (`.form-control`). Fixed with scoped `[data-theme="dark"] .btn { }`-style overrides in `assets/styles.scss`.
- **`.border`/`.border-top` were missed in that original pass and found later (2026-08-04), reported by the user as a light outline around the "AI Insight of the Day" card in dark mode.** Both bake in `border(-top): 1px #e1e4e8 solid !important` — `.theme-border` (the custom class meant to make these theme-aware, applied alongside `.border` on `learning-board.html`, `topic-card.html`, `repo-card.html`, `post-card.html`) only sets `border-color: var(--border)` with no `!important` of its own, so it was silently losing the cascade to Primer's `!important` the entire time, on every element using this pairing, not just the one that got noticed. Fixed the same way as `.Box`/`.form-control`: `[data-theme="dark"] .border, [data-theme="dark"] .border-top { border-color: var(--border) !important; }`.
- **Two rounds were needed for the buttons specifically.** The first round only overrode `color`/`background-color`, which turned out insufficient — classic Primer buttons paint a light `background-image` gradient *on top of* `background-color`, so the gradient kept showing through even with the color "fixed." Second round added `background-image: none !important` (and `!important` throughout that block generally, since Primer's own button rules had enough specificity/layering that plain unweighted overrides weren't reliably winning — unlike `.theme-fg`/`.theme-surface`, which only ever fight a single Liquid-baked class, not a multi-layer vendor component). If a Primer class still looks light after adding a `[data-theme="dark"]` override, suspect `background-image` before assuming the override didn't apply at all.
- `.trivia-btn` (`learning_board.html`) carries Primer's bare `.btn` class too (`btn.className = 'btn text-left p-2 text-normal f6 trivia-btn'` in its JS) — same gradient issue, covered by the same fix.

**Resolved, not just documented:** the site previously had `#0366d6` and `#0969da` — two different "Primer blue" values — coexisting for the same role across includes. Both now resolve through `--accent`/`--accent-solid`. Two more cross-theme inconsistencies were resolved while converting everything for the live toggle (previously invisible since only one theme ever rendered, but would look like a bug the moment someone actually clicks it): `learning_board.html`'s `.trivia-btn:hover` now uses `--accent-bg` in both themes (was accent-tinted in light, neutral gray in dark), and `masthead.html`'s bio paragraph now uses `--fg-muted` in both themes (was full-bright `text-white` in dark, muted `text-gray` in light).

`.aurora-text` (see Component Patterns) remains a deliberate exception — a fixed rainbow gradient (`#FF0080, #7928CA, #0070F3, #38bdf8`), chosen explicitly instead of the token palette for that one flourish; don't "fix" it to use `--accent`.

## Typography
- Site-wide font is Fira Sans (weights 400/500/600/700 — the actual set used anywhere on the site), self-hosted via 8 `@font-face` rules in `assets/styles.scss` (`assets/fonts/*.woff2`) instead of loaded live from Google Fonts, 2026-08-03 — see `.ai/architecture.md` for why (removes 2 cross-origin request hops). Only the `latin`/`latin-ext` Unicode-range subsets are included; this site has no cyrillic/greek/vietnamese content. Falls back to the explicit system stack (see `.github-component` in `assets/styles.scss`) if the web font fails to load for any reason: `-apple-system, BlinkMacSystemFont, "Segoe UI", Helvetica, Arial, sans-serif, "Apple Color Emoji", "Segoe UI Emoji", "Segoe UI Symbol"`. `.github-component` (repo-card.html/topic-card.html) deliberately keeps only the system stack, not Fira Sans — it exists specifically to look like authentic GitHub UI.
- Type scale is Primer's `f1`(largest)–`f6`(smallest) classes, plus `text-bold`, `lh-condensed` (tight line-height for headings/titles).
- `font-family: monospace` is used exactly once, deliberately: YouTube timestamp labels (`youtube_feed.html`) — keep monospace reserved for that "data/timestamp" feel, don't default to it for other UI text.

## Spacing
Primer spacing utilities (`p-3`/`p-4`/`p-5`, `mb-4`/`mb-5`/`mb-6`, `my-6`, `mt-6`) handle block-level spacing. Flex `gap` is set inline in the 6–32px range depending on density:
- `6px`–`8px`: icon-to-label gaps within a single control
- `12px`: gaps between small repeated items (card list, pill row)
- `32px`: gap between major columns (e.g. the two-column split in `thoughts.html`)

## Shadow
Prefer Primer's `box-shadow-small` / `box-shadow-medium` / `box-shadow-large` utility classes. Custom `rgba(0,0,0,…)` shadows are reserved for hover-lift states and floating/fixed elements that need a stronger cue:
- Hover-lift on cards: `0 4px 20px rgba(0,0,0,0.12)` (subtle) up to `0 12px 28px rgba(0,0,0,0.12)` (trivia board hover)
- Preview Rail / preview panel (floating page nav): `2px 2px 8px rgba(0,0,0,0.08)`, `4px 4px 16px rgba(0,0,0,0.12)`

## Motion
Plain CSS `transition` for hover/simple state changes; the Web Animations API (`element.animate()`) for the one interaction that needs spring-like overshoot (accordion open/close — see below). No animation library.

Standard `transition` durations:
- `0.15s ease` – hover state color/border changes (buttons, pills)
- `0.2s`–`0.3s ease` – transform/box-shadow hover-lifts, opacity fades, filter transitions
- `0.4s ease` – larger transforms (photography carousel slide)

**Bounce/overshoot easings** (all `cubic-bezier` "back-out" curves — the control points intentionally exceed `[0,1]` to produce a visible overshoot past the resting value, approximating spring physics without a JS spring library). **Only ever use these on a property that isn't floored/ceilinged at its target** — see the `EASE_OUT` note below for why:
- Accordion open: `cubic-bezier(0.34, 1.56, 0.64, 1)`, 580ms — strong overshoot. Safe: height is growing toward a target with no ceiling.
- Collapse-arrow rotation: `cubic-bezier(0.34, 1.4, 0.64, 1)`, 420ms (CSS `transition`, in `assets/styles.scss`). Safe: `transform: rotate()` isn't clamped in either direction.
- Preview Rail tick/preview morph: `cubic-bezier(0.22, 1.4, 0.36, 1)`, 400ms (tick scale) / 250ms (preview panel), in `_includes/floating_toc.html` — a gentler overshoot than the accordion curves, since it's a continuous hover-driven scale rather than a one-shot open/close.
- Joined-list grouping, opening/separating direction only: `cubic-bezier(0.34, 1.56, 0.64, 1)`, 580ms (same curve as accordion open) — `margin-top`/`border-radius` growing from 0, no ceiling.

**Close/accelerate — no overshoot — `cubic-bezier(0.4, 0, 1, 1)`** (Material's standard accelerate curve): used for **accordion close** (460ms, `assets/js/accordion.js`) and the **joined-list grouping's closing/joining direction** (460ms, `assets/js/accordion-grouping.js`). Non-overshoot is a correctness requirement here, not a style choice — `height`, `border-radius`, and `padding` are all floored at 0, and any easing curve whose eased progress exceeds 1.0 (every bounce curve above) makes the animated value hit 0 *before* the animation's nominal duration ends, then sit there clamped and visibly frozen until the clock catches up. Verified by plotting `cubic-bezier(0.32, 1.2, 0.64, 1)` (the close curve used until this was found and fixed): its eased progress exceeds 1.0 from t≈0.62 to t≈0.97 — the last third of the animation was a dead stall.
- **Two decelerate curves were tried and rejected before this:** the reference's own `EASE_OUT` token (`cubic-bezier(0.16, 1, 0.3, 1)`, `ease.ts`) and Material's standard *decelerate* curve (`cubic-bezier(0, 0, 0.2, 1)`). Both are real, both non-overshooting, both still read as "fast shrink, then it just sits there for a beat, then resolves" — plotted numerically, they hit 99.6%/94.7% progress respectively by 70% of the duration, front-loading nearly all their motion into the first half regardless of how gentle the curve is. That's not jank or a sequencing bug — it's the wrong *direction* of easing for this motion. A **decelerate** shape (fast start, slow settle) is correct for an *entering*/*expanding* element (OPEN's own curve), but the mirror-image **accelerate** shape (slow start, fast finish) is what a *closing*/*collapsing* element should use, per standard motion-design convention (Material's own guidance draws this exact distinction). Switching CLOSE to Material's accelerate curve builds speed through the motion and finishes decisively — no crawl at the end, because the curve's slow portion is at the *start*, not the end. Verified non-overshooting (dense-sampled max Y = 1.0 exactly).
- **Never give a close/shrink/collapse-toward-zero animation an overshoot easing — check whether the target is a floor (or ceiling) before reusing one of the bounce curves above.** And for non-overshoot curves specifically: match the easing *direction* to whether the element is entering (decelerate) or exiting (accelerate) — a decelerate curve on an exit can look mathematically correct (never overshoots, monotonically approaches the target) and still read as "stalls, then snaps," no matter how much the tail is flattened, because the crawl is in the wrong place. Plot the curve, don't just eyeball or reuse one because it's "close enough."

Reuse these curves for any new bounce/morph interaction rather than inventing new ones — pick a bounce curve for growing-with-no-ceiling motion, the close/decelerate curve above for anything animating toward a floor/ceiling. All bounce animations are skipped (native instant toggle/no scale change) when `prefers-reduced-motion: reduce` is set — the accordion does this via a JS `matchMedia` check (`assets/js/accordion.js`), the Preview Rail via a plain CSS `@media (prefers-reduced-motion: reduce)` override (no JS needed, since it's a pure CSS transition either way).

**Continuous/looping motion** (not bounce, runs indefinitely rather than settling): the Aurora Text gradient shift (`6s linear infinite`, `assets/styles.scss`), the blockquote typing cursor blink (`0.8s step-end infinite`), and skeleton loading placeholders (`.skeleton`, `2s cubic-bezier(0.4, 0, 0.6, 1) infinite`, keyframe `50% { opacity: .5 }`) — all three respect `prefers-reduced-motion` (the gradient freezes at its start position, the typing effect is skipped entirely, `.skeleton` stops animating and holds a static `opacity: 0.7`).
- **`.skeleton`'s exact timing/curve is copied from shadcn/ui's real `Skeleton` component** (`ui.shadcn.com/docs/components/base/skeleton`, Tailwind's `animate-pulse` under the hood) — fetched and confirmed directly rather than assumed from the name, since "skeleton loader" is sometimes a moving left-to-right gradient shimmer instead (a different, unrelated pattern the user considered and explicitly didn't want; shadcn's own version is a plain uniform opacity pulse, no movement). Reuse `.skeleton` as-is for any future loading placeholder rather than inventing a new timing.

**Reveal timing:** the blockquote typewriter (`assets/js/quote-typing.js`) reveals one character every 35ms — not a `cubic-bezier`, just a fixed interval. Reuse this constant if another character-reveal effect is ever added, rather than picking a different speed.

## Component Patterns
- **Collapsible section (bouncy accordion):** native `<details class="details-reset animated-details" open>` + `<summary>` holding an `<h2>` + rotating chevron `<svg class="collapse-arrow">`, with exactly one direct content `<div>` after `<summary>`. The base structural CSS (`.animated-details`, `.collapse-arrow`) lives in `assets/styles.scss` — a single shared definition, not duplicated per-include. `assets/js/accordion.js` (loaded once site-wide via `_includes/footer.html`) intercepts the `summary` click and drives the open/close height/opacity animation via WAAPI using the bounce easings above; it targets every `details.animated-details` on the page automatically, so a new collapsible section needs no JS of its own — just follow the markup shape (one `<summary>`, one content `<div>` after it). This is the pattern for every major homepage section (Writing, Reclaiming the Algo, Photography) plus the Gratitude teaser — use it for any new top-level section.
- **Skeleton loading placeholders (2026-08-03):** `.skeleton` (see Motion section for the exact timing/curve, copied from shadcn/ui's real component) is a plain `span`/`div` sized to match the shape of the real content it stands in for — no text, no icon, just a pulsing gray block. Applied in 3 places, each following the same pattern: a skeleton container sits alongside (not inside) the real content container, one is `display: none` while the other shows, and the JS that populates the real content flips which one is visible once it has data.
  - **`youtube_feed.html`:** `#yt-skeleton` (category-pill/2-line-title/channel/summary-shaped bars) vs `#yt-info` (the real category/title/channel/summary/link/buttons markup) — `loadVideo()` flips them on every call (idempotent; harmless that Prev/Next re-triggers it after the first load).
  - **`learning_board.html`:** `#trivia-skeleton` (2-line question/source-line/3-option-bar shape) vs `#trivia-content` (the real question/options/reveal markup) — `loadQuestion()` flips them, same idempotent pattern; the no-trivia-data early-return branch flips them too, so the "Oops!" fallback message is reachable.
  - **`thoughts.html`:** `#medium-loading` holds *two* skeleton shapes side by side — 3 stacked row-blocks (`.medium-skeleton-row`, matching the tablet/desktop `.medium-card` shape) and 4 small blocks in a horizontal row (`.medium-skeleton-story`, matching the phone-only `.medium-story-card` shape) — CSS-toggled by the same `≤767px` breakpoint the real cards switch on, not a JS decision. No fetch-driven toggle needed either — `container.innerHTML = ''` in the fetch's success *and* error paths already replaces the whole thing wholesale before real cards (or the error message) get appended, so the skeleton just needs to be what's there by default.
- **YouTube click-to-load facade (`youtube_feed.html`, 2026-08-03):** a static thumbnail + play button (`#yt-facade`, `.yt-facade`/`.yt-facade-thumb`/`.yt-facade-play`) instead of a live `YT.Player` embed by default — the real embed only loads once the user clicks the facade or a timestamp. Not a visual-polish decision: a live YouTube embed loads YouTube's entire player app unconditionally (~1MB, ~700ms of main-thread time, confirmed via PageSpeed Insights), whether or not the visitor ever presses play — the facade defers that cost to an actual expressed intent to watch.
  - **Thumbnail source:** `https://i.ytimg.com/vi/<videoId>/hqdefault.jpg` — guaranteed to exist for every YouTube video (unlike `maxresdefault.jpg`, which isn't generated for all videos and can 404). `i.ytimg.com` is `preconnect`ed in `header.html` (added 2026-08-04, ~200ms est. LCP savings per PageSpeed Insights — this entry previously claimed it was "already preconnected from before this feature existed," which was stale/wrong; no preconnect tag for this origin existed anywhere in the codebase until this date, most likely lost when the Google Fonts preconnect hints were removed during font self-hosting and never re-added for YouTube).
  - **Stray outline around the whole facade, fixed 2026-08-04.** First diagnosis (wrong, but harmless): assumed it was `#yt-facade-thumb`'s `<img>` rendering a default browser border while src-less before `loadRealPlayer`/`loadVideo` sets one — added `border: none` there, which compiled and deployed but didn't fix it, confirmed by a follow-up screenshot showing the border still present live. **Actual cause:** `#yt-facade` is a `<button>` sized `position: absolute; inset: 0` — it fills the *entire* 16:9 video box, not a small icon, so the browser's default focus outline traces that whole rectangle rather than a subtle ring around a small button, reading as a stray full-frame border (visible after a click or Tab lands focus on it). Fixed with `outline: none` directly on `.yt-facade` — safe because `.yt-facade-play` already turns solid red and scales up on `:hover`/`:focus-visible`, a clearly visible focus indicator in its own right, so nothing becomes invisible-on-focus by removing the browser default. The `.yt-facade-thumb { border: none; }` from the first attempt was left in place (harmless, technically still a valid defensive guard) rather than reverted.
  - **Shorts' facade thumbnail stays landscape on mobile, fixed 2026-08-04.** `#yt-player-container` starts landscape (`aspect-ratio: 16/9`) but `loadVideo()` used to unconditionally shrink it to a narrow portrait box (`9/16`, `max-width: 320px`) for any video whose URL contains `/shorts/` — on every call, whether the facade or the real player was showing. User: "for mobile, shorts thumbnails should be in landscape as well. Left and right of the photo should be blurred to fit landscape." **Verified against real data before writing any fix, not assumed:** pulled 3 real Short video IDs from `_data/youtube.json`, fetched their actual `hqdefault.jpg` thumbnails, and read the downloaded JPEGs directly — all of them, and a regular video's thumbnail for comparison, are the identical fixed 480×360 dimensions. YouTube doesn't serve a true portrait image at this endpoint; instead it **already composites a Short's portrait content centered in that landscape frame, with a blurred/darkened duplicate of the adjacent content filling the left and right sides** — confirmed visually on two separate Shorts. The "blurred to fit landscape" look the user asked for already exists in the source image; forcing the container narrow and `object-fit: cover`-cropping it down to a thin vertical strip is what was destroying it. **So the fix doesn't build a blur effect — it stops discarding the one YouTube already provides:** on mobile specifically, while the facade is still showing (`ytReady && ytPlayer && ytPlayer.cueVideoById` false — the same check `loadVideo()` already uses to decide whether to touch the facade thumbnail at all), the container now stays landscape and `.yt-facade-short .yt-facade-thumb { object-fit: contain; }` shows the whole composited image with zero cropping. Desktop's facade, and *any* viewport once the real player has actually loaded (`loadRealPlayer()` calls the new `setVideoContainerAspect(true)` the moment the facade is dismissed, for correct native-shape playback), are unchanged from before. New `setVideoContainerAspect(isPortrait)` helper and hoisted top-level `videoContainer`/`currentVideoIsShort` replace what used to be a locally-scoped, duplicated inline resize in `loadVideo()` alone.
  - **`loadRealPlayer(seekTime)` is the single entry point**, called from both the facade's own click handler and every timestamp button's `onclick` — a timestamp click is just as clear a "play this" signal as the facade itself, so it has to work identically whether the facade is still showing or already dismissed: if the player already exists, just seek; if not, request YouTube's `iframe_api` script for the first time (only ever requested here, never eagerly on page load) and defer the seek until `onReady` fires.
  - **Swipe/drag to browse Prev/Next, replacing the buttons entirely (2026-08-05).** User: "Can we have this for our yt card instead of the previous and next button? ## Known Gaps
- `assets/js/accordion.js` assumes exactly one content `<div>` directly after `<summary>` inside `details.animated-details`. A collapsible section with a different internal shape (e.g. multiple top-level children) won't animate correctly — wrap it in one container div first.
- `assets/js/quote-typing.js` has no opt-out mechanism. Every `<blockquote>` on every page gets typed, with no way to exclude a specific one (e.g. a long quote in a future blog post where typing it out would be more annoying than delightful). If that's needed later, the simplest fix is an opt-out class (e.g. skip `blockquote.no-type`) checked in the `document.querySelectorAll('blockquote')` line.
- View Transition API support is Chromium-first (Safari 18+/Firefox support varies by version) — the theme toggle degrades gracefully to an instant swap elsewhere, but the rectangular wipe itself is a Chromium-only visual, not a cross-browser guarantee.
