## Tech Stack

- **Vite + React 19 + TypeScript**, `npm create vite@latest -- --template react-ts`.
- **Tailwind v4** via `@tailwindcss/vite` (no separate `tailwind.config.js` — configured through `@import "tailwindcss"` in `src/index.css`), used only by shadcn/beui-sourced components. Site content wearing Primer classes doesn't use Tailwind utilities at all — the two systems coexist without collision since neither's class names overlap.
- **Primer CSS reused directly, not redesigned in Tailwind.** `src/styles/primer.css` is a copy of the live site's PurgeCSS-trimmed `assets/vendor/primer.css`; `src/styles/site.scss` is a copy of `assets/styles.scss` (Jekyll front matter stripped, one port-note comment added). Import order in `src/main.tsx` matters and must not be reordered: Tailwind Preflight (via `index.css`) → `primer.css` → `site.scss` — Preflight resets element defaults, Primer re-establishes its own baseline for anything wearing Primer classes, site.scss's tokens/overrides load last.
- **shadcn CLI**, configured in `components.json` (`style: "base-nova"`, `iconLibrary: "lucide"`). One custom registry configured: `@beui` → `https://beui.dev/r/{name}.json`. `npx shadcn search @beui https://magicui.design/registry.json https://ui.aceternity.com/registry.json -q "<term>"` (from inside `component-lab/`) searches multiple registries even though only `@beui` is a configured namespace — magicui/aceternity are passed as raw registry URLs, not namespaces, since neither has a stable `@name` the CLI recognizes.
- **react-router-dom** (pinned to a real specific version, not whatever `npm audit fix --force` suggests — that command has previously *downgraded* this package to a version with *more* CVEs; check `npm view react-router-dom version` and pin manually if `npm audit` flags something). Two route shapes: `/` (home) and `/:year/:month/:day/:title/` (post), matching the live site's `permalink: /:year/:month/:day/:title/` in `_config.yml` exactly.

## Component-sourcing rule

**For every new section or interactive piece, search the beui/magicui/aceternity/shadcn registries first, before hand-porting.** This was an explicit steer partway through the port (2026-08-06) — install-then-adapt a real component where one genuinely fits the shape of what's needed, hand-port only where nothing does. Don't skip the search step even when a hand-port feels obviously necessary; the search itself is cheap and the fit is sometimes non-obvious.

**Checked so far, found not to fit (don't re-litigate without new information):**
- `@beui/bouncy-accordion` — real, installable, but architecturally wrong: it's a single-list, always-single-open accordion (one `items` array, one active id at a time). This site's 3 "groupable" homepage sections are independent page-level compositions with arbitrary complex children (a swipe carousel, a canvas gallery), multi-open on desktop, single-open only on mobile — a shape `bouncy-accordion`'s data model can't represent without giving up real desktop behavior.
- Carousel/swipe search terms (`carousel`, `swipe`) — only generic testimonial/image carousels (aceternity's `carousel.json`, `apple-cards-carousel.json`) or iOS-style swipe-to-reveal-actions patterns (`@beui/swipeable-list`), not the specific mechanic needed: a 3-slide prev/current/next viewport, axis-locked drag, pixel-threshold commit, snap settle.
- Blog-card/quiz search terms — only full magazine-page listing layouts (`blog-with-categories`, `blog-with-search-magazine`) or unrelated widgets, nothing matching a compact card tray inside a homepage section, or a quiz-into-swipe-carousel.
- Hero/profile search terms (for Masthead) — only marketing-landing-page hero sections (headline + CTA), nothing matching an avatar+bio+contact-info+social-icons personal header block.

**Still worth checking when reached:** `@beui/preview-rail` ("Codex app-inspired navigation rail with compact ticks") for the floating Preview Rail nav — name and description both look like a plausible fit, not yet actually tried.

## Data Flow

**`_data/*.json` files are imported directly from the real path, not duplicated**, e.g. `import gratitudeData from "../../../_data/gratitude.json"` from a `src/components/*.tsx` file. This keeps one source of truth with what GitHub Actions regenerates on `master`'s own schedule (gratitude/learning/youtube/medium, twice-daily to daily) — a copied-in file would silently go stale. `vite.config.ts`'s `server.fs.allow` is widened to the repo root specifically so the dev server can serve these cross-root imports; don't narrow it back without providing another way to reach `_data/`.

**One exception: `_data/social_media.yml` is NOT imported directly** — it's YAML, not JSON, Vite has no YAML loader installed, and it's hand-maintained (not GitHub-Actions-regenerated) so staleness isn't a real risk. `src/data/social_media.json` is a one-time converted copy; if the source `.yml` is ever hand-edited, re-run the conversion (a `js-yaml`-based one-off script, not a checked-in dependency — see the commit that created this file for the exact command).

**Fonts, images referenced by the app itself** (avatar, Fira Sans woff2s) are copied into `component-lab/public/`, not cross-root-imported — these are static binary assets, not data that goes stale, and Vite's dev server / build both handle `public/` uniformly without the `fs.allow` complexity JSON imports needed.

## Shared Accordion System

`src/hooks/useAccordionGroup.tsx` (context: every registered accordion's open state, joined-border computation for the 3 "groupable" sections, mobile single-open enforcement) + `src/hooks/useAnimatedDisclosure.ts` (the WAAPI bounce open/close animation itself, shared between `Accordion.tsx` and `Gratitude.tsx`'s own differently-headed disclosure) + `src/components/Accordion.tsx` (the shared shell: header row, goo-popover trigger, joined-border classes, chevron).

**Hard-won invariants — violating any of these reintroduces bugs that took a full multi-round debugging session to find (2026-08-06):**

1. **`isOpen(id, defaultOpen)` / `toggle(id, defaultOpen)` must always be called with the accordion's own `defaultOpen` prop as the second argument.** This is the fallback used for any id never yet explicitly toggled, and it's what makes `open` state correct from the very first render — there is no mount-effect that seeds it separately anymore, and there must not be one added back. (History: `open` used to be seeded by a mount effect calling `toggle()` a render after the component's own first render, so it lagged `true` by one render for every `defaultOpen` accordion — root cause of a whole chain of bugs: a spurious close-then-reopen flash on mobile from multiple sections' mount-triggered toggles fighting under the mobile-single-open rule, then a stale animation clobbering the fix for that.)

2. **`useAnimatedDisclosure` is the *sole* owner of its content element's `display` style.** The JSX rendering that element must never set `display`, reactively or statically. React writes inline styles synchronously during its own commit, before any effect runs — a reactively-set `display` would already be flipped before the animation's effect gets a chance to measure/transition the element, breaking the animation outright (tried once, reverted).

3. **Any component that populates real content over a skeleton placeholder on mount must do so in `useLayoutEffect`, not `useEffect`**, if it lives inside an `Accordion`. `Accordion`'s own open-state code runs in `useLayoutEffect` (pre-paint); a plain `useEffect` runs one render-pass later (post-paint), so the skeleton — shorter than the real content — paints first, already "open," then swaps to taller real content a moment later. Reads as a second, separate opening. `YoutubeCarousel.tsx` and `TriviaBoard.tsx` both do this correctly; match their pattern for any new carousel-style child.

4. **Any `ResizeObserver` watching an element that can be hidden by an ancestor's `display:none` (i.e. anything inside an `Accordion`) must ignore `0`-height reports.** A hidden ancestor makes the observed element report `0`, not a real collapse — if written through, it becomes a stale leftover height that the *next* open animation reads before the observer's own (asynchronous, not synchronous with the reopen) next fire can correct it. Symptom: animates to a too-small target, then snaps to full size once the observer catches up. See the `> 0` guards in `YoutubeCarousel.tsx`/`TriviaBoard.tsx`'s own `ResizeObserver` callbacks.

If a new bug shows up anywhere near open/close animation, suspect one of these four categories (state lag, style ownership conflict, effect-timing-vs-paint, or a ResizeObserver/async-correction race) before assuming something new.

## Component Conventions

- **Fidelity over redesign**: each ported section mirrors its `_includes/*.html` source's DOM structure, class names, and inline styles closely — this is a like-for-like port, not a visual refresh. Deviations are called out explicitly in the component's own top comment, with the reason (e.g. `MediumTray.tsx` renders real JSX cards instead of the original's raw HTML-string-into-`innerHTML`, since article titles/excerpts come from Medium's own RSS content and JSX's default escaping is strictly safer for the same visual result — a deliberate fix, not a fidelity gap).
- **Imperative-refs pattern for animation-sequence-sensitive carousels.** `YoutubeCarousel.tsx` and `TriviaBoard.tsx` are both transliterated close to 1:1 from their vanilla `<script>` sources — refs standing in for `getElementById`, plain mutable variables closed over inside one big mount effect standing in for the original's module-scoped `var`s, rather than modeling `currentIndex`/player state/drag tracking as React state. The swipe-settle-then-swap-data choreography (drag → commit threshold → WAAPI slide → swap underlying data → instant-reset transform) is precisely sequenced; re-deriving it as reactive state risks breaking that sequencing for no visual benefit. Kept as two separate self-contained copies rather than one shared hook, matching the original site's own relationship between the two (`learning_board.html`'s own comments say it copied `youtube_feed.html`'s wiring, not that the two ever shared a file).
- **Cross-component coordination becomes ordinary React state/props, not global functions.** The original's `window.filterTrivia` (Medium's category filter buttons reaching into a separately-included trivia widget) is now `activeFilter` state lifted to `InsightsWriting.tsx`, passed down to both `MediumTray` and `TriviaBoard` as props. Look for this pattern — a `window.*` global hook in the original almost always means "this needs to become lifted state," not "reproduce the global."
- **`useAccordionGroup`'s mobile single-open / `isDesktopWidthAtMount()` (`src/lib/viewport.ts`)** replaces `_layouts/home.html`'s own synchronous pre-paint script that force-closes every `#accordion-group` section on mobile. Any new `Accordion` instance that should default open on desktop / closed on mobile (i.e. any of the "groupable" homepage sections) must pass `defaultOpen={isDesktopWidthAtMount()}`, not a hardcoded boolean.
