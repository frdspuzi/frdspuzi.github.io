## 1. Core Architecture & Stack
See [.ai/architecture.md](architecture.md) for the full breakdown. Short version: Jekyll + Primer CSS + GitHub Pages, no JS framework, no bundler. AI/photo content is generated by Node scripts in `.github/scripts/`, scheduled by workflows in `.github/workflows/`, written to `_data/*.json`, and rendered statically by Liquid in `_includes/*.html` at build time.

## 2. Key Files & Data Pipeline
- `_layouts/home.html`: The homepage layout. Renders (in order) masthead → gratitude → youtube feed → thoughts (writing + trivia) → photography, in either a `stacked` or sidebar arrangement depending on `_config.yml`.
- `_includes/floating_toc.html`: Hover-reveal nav pinned top-left (desktop) / bottom-right FAB (mobile, `≤767px`). Its anchor list is the actual source of truth for page order — keep it in sync if sections move.
- `_includes/learning_board.html`: The interactive AI trivia widget, embedded inside `thoughts.html`'s right column (not its own top-level homepage section).
- `_includes/gratitude.html`, `_includes/youtube_feed.html`, `_includes/photography.html`, `_includes/thoughts.html`: One self-contained feature each, own inline `<script>`/`<style>`.
- `assets/styles.scss`: The only stylesheet; imports Primer + `_sass/_highlight-syntax.scss`, then custom rules.
- `.github/scripts/`: `fetch_unsplash.js`, `fetch_youtube.js`, `generate_gratitude.js`, `generate_learning.js` — all Node, all hit Gemini and/or a media API, all write directly into `_data/`.
- `.cursorrules`: Cursor-facing operational rules (PowerShell syntax, git pull/rebase-before-push, conventional commits, API waterfall pattern, writing tone). Still applies — this handoff doesn't replace it, `CLAUDE.md` just surfaces the same rules for Claude Code.

Curated single-video feed meant to bypass algorithmic feeds. `fetch_youtube.js` pulls the top 3 recent videos from a hardcoded channel allowlist (Tech/Productivity/Islamic Studies), plus a 20%-of-the-time "Discovery" keyword search to avoid a filter bubble. Every video's selection reasoning (including rejects) is logged to `_data/youtube_eval_log.json` for transparency; winners go to `_data/youtube.json`. ### Floating nav / Preview Rail (`_includes/floating_toc.html`)
A single Preview Rail at all viewport widths — a 48px vertical strip of 5 tick-mark buttons pinned top-left. There is no separate mobile FAB anymore (the original bottom-right `☰` tap-to-expand button was removed per explicit user request; the rail's ticks are directly tappable on touch, they just don't get the hover magnify/preview effect since touch doesn't fire `mouseenter`/`focus`). On hover/focus (desktop), a tick scales itself and its neighbors by distance (1/0.68/0.44/0.25) and opens a floating preview panel beside the rail with that section's label + one-line description. Ticks are `<button>` + `scrollIntoView()`, not `href` anchors — anchor links no-op on repeated clicks to an already-set hash, buttons don't. Active-section highlighting watches scroll position at a 40% viewport threshold. **Verified current anchor/section order:** About → Gratitude → Reclaiming the Algo → Insights & Writing → Photography — the `sections` array in this file's own `<script>` is the actual source of truth; always check it + `home.html` directly rather than trusting a written description of page order.

## 4. AI API Orchestration & Fallbacks
- `ai-daily-content.yml` is a daily (`30 0 * * *` UTC) orchestrator that calls the youtube/gratitude/learning child workflows (`ai-youtube.yml`, `ai-gratitude.yml`, `ai-learning.yml`) via `uses:`/`secrets: inherit`; each child also has its own `workflow_dispatch` for standalone manual runs. `unsplash.yml` is separate and runs on its own twice-daily schedule (`0 0,12 * * *`).
- Gemini's free tier is tightly rate-limited (as low as 20 requests/day on some models). All scripts use a waterfall fallback: try the smartest model first, degrade to a lighter model on `429`/`503` rather than failing the pipeline outright.
- **Top-tier model bumped to `gemini-3.6-flash` (2026-07-27)**, replacing `gemini-3.5-flash` as the first entry in the waterfall array in `generate_learning.js`, `generate_gratitude.js`, and `fetch_youtube.js` (which also has a second, standalone hardcoded reference for its Vertex AI video-watching call, updated too). The rest of the waterfall (`gemini-2.5-flash` → `gemini-3.1-flash-lite` → `gemini-2.5-flash-lite`) is unchanged. If Gemini releases another model ahead of this in capability, this is the pattern to follow: update the array's first entry (and `fetch_youtube.js`'s separate hardcoded one) in all three scripts, keep the rest of the fallback chain as-is.

**Runtime dark/light theme toggle — Rectangle variant (2026-07-27):** The largest single change of the project so far, touching nearly every template file. Reference: https://beui.dev/components/motion/theme-toggle (React + Framer Motion + `next-themes` + View Transition API in the original). Placement: bottom of `#preview-rail` in `_includes/floating_toc.html` (last flex item, not a separately fixed-position element — always sits directly below the nav ticks regardless of tick count). - **The architectural shift:** dark mode used to be resolved once, at Jekyll build time, from `site.style` in `_config.yml` — the "other" theme's values were never even sent to the browser, so no JS toggle could have worked before this. `assets/styles.scss`'s token block is now **two** blocks — `:root { }` (light defaults) and `[data-theme="dark"] { }` (dark overrides) — both always shipped; a `data-theme` attribute on `<html>` picks which applies, instantly, no rebuild. `_config.yml`'s `style:` setting still matters, but only as the *initial* default (`<html data-theme="{{ site.style }}">` in `header.html`) — a visitor's actual choice, once made, is read from `localStorage` by a tiny synchronous inline script placed early in `<head>` (before first paint, so no flash of the wrong theme for returning visitors).

**Follow-up: "Reclaiming the Algo" left a huge gap after close→reopen — defensive fix, not a confirmed root cause (2026-07-27):** User reported a large gap below the video/info box specifically after closing and reopening this one section — confirmed via diagnostic questions to happen with *any* video (not tied to title length) and *only* this section, not Insights & Writing or Photography. That isolates it to the one thing unique to this section: the embedded YouTube iframe, loaded async via the IFrame API.
- **Leading theory (not confirmed — user wasn't able to check DevTools):** `accordion.js`'s `open()` measures `content.scrollHeight` once, synchronously, right as the open animation starts, then holds that value via `fill: 'forwards'` until `onfinish` clears it back to `auto`. **Follow-up: the last two "doesn't snap" bugs, found via a temporary 5x slowdown, and the difference between a bug and physics (2026-07-27):** User reported "still doesn't snap" after all 5 fixes above — each had been a real, verified bug, but the underlying complaint kept surviving. - **WAAPI `fill: 'none'` default:** `content.animate()` in `accordion.js` never set a `fill` mode, so the instant an animation's active duration elapsed, the browser un-applied its effect and `content` reverted to its pre-animation underlying value — for however long it took the `onfinish` callback to actually run and set the real final inline styles. On close, that meant a one-frame flash back to full height right as the animation finished, before the manual cleanup corrected it — user's own words once slow motion isolated it: "The slomo does animation right. Once the animation of closing was done, it snaps." - **Padding not included in the height animation:** a box can never render shorter than its own padding. `content` (the `<div class="p-4 ...">` inside each section) only ever had `height` animated, never its padding — so as height approached 0, the box visually stopped shrinking once it hit the padding floor (~32px for Primer's `p-4`) and sat there as a residual "empty line" for the rest of the close, until `details.open = false` finally hid it via native `[open]`-removal, which is what actually produced the visible snap. - **What's left is expected, not a bug:** after both fixes, the user asked "why doesn't it snap seamlessly" — the very last, tiny settle at the end of any eased transition (ours, or the reference's own spring — springs settle the same way) is inherent: velocity approaches zero asymptotically, movement-per-frame drops below what's visually perceptible before the curve is mathematically done, and the eye reads the final sub-pixel resolve as a discrete "snap" rather than a continuation of motion already read as "stopped." Not fixable by construction for any finite-duration eased curve, and far less perceptible at real speed than the 5x-slowed diagnostic build — confirmed the diagnostic slowdown itself was the reason this last artifact was visible at all.

**Follow-up: the "sub-pixel tail" explanation was wrong — the real cause was the CLOSE curve's shape (2026-07-27):** After the `fill:forwards` and padding fixes above, user reported the transition still "isn't seamless": smooth, then a visible gap that just sits there, then a snap — every time, completely consistent. Two theories were checked and ruled out first: (1) WAAPI/CSS-transition desync between `content`'s height animation and the grouping box's border-radius/margin transition — re-read the code, both are triggered synchronously in the same call stack (`accordion:willclose` fires before `content.animate()` starts), no structural gap between them; (2) main-thread jank from animating non-composited layout properties (`height`/`padding`/`margin-top`/`border-radius` all force reflow, unlike `transform`/`opacity`) — plausible in general, but random jank from thread contention wouldn't be "every time, exactly the same," so this was set aside as secondary at best. The actual cause, found by numerically plotting the CLOSE easing curve's progress-over-time (Node script, same discipline as every other curve check this session): `cubic-bezier(0.16, 1, 0.3, 1)` — the real bouncy-accordion reference's own `EASE_OUT` token, adopted a few rounds ago specifically *because* it was verified non-overshooting — reaches **99.6% progress by 70% of the animation's duration**. That's not a bug in the sense of "wrong," but on a full section's height (much larger, more prominent than whatever the reference itself uses this token for) it reads exactly as "fast shrink, then it just sits there, then resolves" — a real, fully consistent perceptual stall, caused by curve shape, not sequencing or performance.

Still verified non-overshooting (never exceeds 1.0 — safe for the floored height/padding/border-radius properties), but keeps meaningfully more motion in the back half (94.7% progress at that same 70%-of-duration mark) so the close doesn't visually stall before settling. OPEN keeps its original overshoot bounce curve, untouched — this only ever affected the non-bounce, floor-constrained CLOSE direction.

**Follow-up: decelerate was still the wrong curve *direction* for a close, not just insufficiently flattened (2026-07-27):** User's next check: "Almost" — confirmed via follow-up as the *same* stall-then-snap pattern, just smaller. That ruled out "needs an even flatter decelerate curve" as the fix (already tried two: `EASE_OUT` then Material decelerate, both front-load progress and both left a residual crawl) and pointed at something structural instead. The actual issue: **a decelerate shape (fast start, slow settle) is simply the wrong direction of easing for a closing/collapsing/exiting element.** Standard motion-design convention (Material's own guidance draws this distinction explicitly) calls for a decelerate curve on *entering*/*expanding* motion (correct for OPEN, unchanged) and the mirror-image **accelerate** curve (slow start, fast finish) on *exiting*/*collapsing* motion — which CLOSE had never used. This curve builds speed through the close and finishes decisively, with the slow portion at the *start* (where attention hasn't focused yet) instead of the *end* (where a crawl reads as a stall) — the structural fix that flattening a decelerate curve could never fully achieve. DESIGN.md's Motion section rewritten to document this and the lesson: **for non-overshoot curves specifically, match the easing direction to whether the element is entering (decelerate) or exiting (accelerate) — a decelerate curve on an exit can be mathematically correct (monotonic, never overshoots) and still read as "stalls, then snaps," no matter how flat the tail is made, because the crawl is in the wrong place.**

**Follow-up: the stylesheet-class version still fought the animation — replaced with a `::after` spacer (2026-07-27):** The class-based fix above survived close→reopen (confirmed no longer wiped), but user's next test surfaced a *different* break: "after the bounce, it doesn't have the bottom padding" — the padding was gone specifically *after* the open animation finished, not before. Root cause: `!important` stylesheet declarations always outrank Web Animations API values in the CSS cascade, regardless of `fill` mode — so `.p-4.accordion-content { padding-bottom: 36px !important; }` was in direct, permanent conflict with `accordion.js`'s own `content.animate([...{ paddingBottom: ... }])` on the exact same property of the exact same element, every single open/close. **The fix isn't a stronger override — it's removing the conflict entirely.** Replaced the `padding-bottom` rule with `.accordion-content::after { content: ''; display: block; height: 12px; }`: a static spacer that never touches `padding-bottom` at all, so there's nothing left for the stylesheet and the animation to contend over. - **General lesson:** never put a `!important` override on a CSS property that a WAAPI/CSS animation *also* targets on the same element — the override doesn't just risk losing (predictable, easy to debug), it can behave inconsistently around the animation's start/end boundaries (worked before the bounce, silently gone after it) since importance is resolved per-property, per-frame, against whatever the animation is doing at that instant. If a property needs *both* a permanent stylesheet value *and* to be safely animatable, keep the override on a property (or a separate element/pseudo-element) the animation never touches, rather than trying to out-rank the animation on the same property.

**Follow-up: skeleton stayed visibly stuck on top of the real content, on both YouTube and Trivia (2026-08-03):** User sent a screenshot showing `#yt-skeleton`'s pulsing bars rendered directly above the fully-populated real YouTube card (title, channel, summary, timestamps all correct) — the skeleton never actually hid. **Follow-up: Medium article list not scrollable on phone (2026-08-02):** User request: "Help make the article list scrollable on phone." `thoughts.html`'s `#medium-posts` (the article card list) already sat inside `.right-column-container`, a fixed-height (`450px` mobile / `648px` desktop) `overflow: hidden` box, with `#medium-posts` itself set to `flex: 1 1 auto; overflow-y: auto; min-height: 0;` — the standard pattern for a scrollable region nested inside the page's own scroll.
- **First two attempts were wrong diagnoses, both no-ops:** (1) added `-webkit-overflow-scrolling: touch` + `overscroll-behavior: contain` to `.custom-scrollbar` (momentum feel / scroll-chaining containment) — user reported "still unscrollable." (2) added `touch-action: pan-y` to the same rule (explicit touch-gesture ownership, since `#medium-posts` is itself `display:flex` full of edge-to-edge `<a>` cards) — user reported "Nope." Both were reasonable-sounding touch/gesture properties but treated the symptom as a *feel* problem when it was actually structural: nothing was scrolling internally at all, so no gesture-recognition property could have helped.
- **Confirmed via a screenshot the user sent:** a third article card was visibly cut off mid-card at the bottom of the 450px box, immediately followed by the next section (the trivia widget) in normal flow — proof that clipping was happening, but at the *outer* `.right-column-container` (`overflow: hidden`, not scrollable), not inside `#medium-posts`.
- **Actual root cause:** `.right-column-content` (the flex-column wrapper *between* `.right-column-container` and `#medium-posts`) was missing `min-height: 0`. A flex item's automatic minimum size defaults to its content's natural (unclamped) size, not `0` — `#medium-posts` already overrode this on itself, but `.right-column-content` one level up didn't, so it grew to fit every article card regardless of the 450px/648px cap, dragging `#medium-posts`'s actual height along with it. `#medium-posts` was therefore never shorter than its own content, so its `overflow-y: auto` had nothing to engage — the only thing clipping the overflow was `.right-column-container`'s `overflow: hidden` one level further out, which just hard-cuts rather than scrolls.
- **Fix:** added `min-height: 0;` to `.right-column-content`. This is the general lesson, not just this one bug — **every level of a flex-column chain leading to a scrollable child needs `min-height: 0`, not just the scrollable element itself**; missing it on an intermediate wrapper produces exactly this symptom (visible clipping outside, but zero internal scroll) and is easy to misdiagnose as a touch/momentum issue because the visual clipping still looks plausible.
