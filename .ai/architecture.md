# frdspuzi.github.io Architectural Context

**Tech Stack:**
- **Site generator:** Jekyll, hosted on GitHub Pages (`master` branch auto-publishes).
- **Layout base:** GitHub's Primer CSS, extended with custom SCSS. `_sass/_highlight-syntax.scss` is the only partial; everything else lives directly in `assets/styles.scss`. **Self-hosted as `assets/vendor/primer.css` (pinned to v11.0.0), linked directly in `header.html`'s `<head>` — not a CSS `@import` inside `styles.scss` anymore (that was the original, template-inherited setup from 2019 until 2026-08-03).** The `@import` cost every page load an extra network round-trip (unpkg's unversioned URL 302-redirected to the pinned one), couldn't load in parallel with `styles.css` (an `@import` is only discovered after the importing stylesheet is itself downloaded and parsed — a serial dependency, not a parallel one), and made the site's core layout/styling depend on a third-party CDN's (unpkg.com) response time for no reason. Fixed the same way the Unsplash photo hotlinking was fixed below: stop depending on another server's response time for something core to the page. To pull in a newer Primer release, see `assets/vendor/primer.css`'s own header comment (a manual `curl` + re-add-the-header-comment step, matching this codebase's existing preference for manual, explicit version bumps over automatic ones — see the cache-busting `asset_version` decision elsewhere in this file).
  - **Stays a separate `<link>`, deliberately not merged into `styles.css` via a Sass `@import` — tried and reverted same day (2026-08-03).** A build-time Sass `@import` (as opposed to the browser-time CSS `@import` this whole entry is about) sounds like a strictly-better version of the same idea — one render-blocking request instead of two, resolved entirely at compile time, no runtime cost. In practice, `jekyll-sass-converter` 1.5.2 (the old, effectively unmaintained Sass toolchain this site's `github-pages` gem pins) has a real bug processing Primer's file that way: it silently inserted two large blocks of pure whitespace (104KB and 16KB) into the compiled output, at the exact boundaries between Primer's own internally-concatenated license comments — confirmed absent from the source file via direct byte inspection, so genuinely introduced by the compiler, not present in what was downloaded. **Don't retry this without a newer Sass toolchain** (this site is locked to whatever version `github-pages`/GitHub Pages' build pins, not something upgradable independently) — the two-requests-in-parallel status quo is safe and already fast; a broken compiled stylesheet is a much worse outcome than one extra (small, same-origin, parallel-loading) HTTP request.
  - **PurgeCSS'd down to only what's actually used, 2026-08-04.** PageSpeed Insights flagged both this file's render-blocking cost *and* 22.5 KiB of it as unused CSS — the same root cause: this site only uses ~119 of Primer's ~1,968 defined selectors. Ran `npx purgecss` once, locally, as a throwaway tool (not a project dependency — no root `package.json` exists in this repo to add it to anyway; only `.github/scripts/package.json`, for CI-only Node scripts). Content sources were every `_includes/*.html`/`_layouts/*.html`/`index.html` plus `assets/js/*.js` (so JS-toggled class strings inside `classList.add()`/`.toggle()` calls get picked up too), with an explicit safelist for ~14 runtime-toggled classes as a precaution — none of which turned out to actually be Primer classes in the first place. Result: 144,991 bytes → ~18,000 (-87.6%), verified by grepping the output for every one of the ~119 real used classes plus base element resets (`html`/`body`/`a`, from normalize.css — PurgeCSS only strips unused class/id selectors, never bare tag selectors) before committing it. See `assets/vendor/primer.css`'s own header comment for the exact safelist and how to re-run this after adding a Primer class no page currently uses — **a class not already used somewhere on the site won't be styled until the purge runs again**, which hasn't come up yet since blog posts are prose-only Markdown, but is a real ongoing cost of this trim, not a one-time one.
- **Fira Sans is self-hosted too (`assets/fonts/*.woff2`, `@font-face` rules in `assets/styles.scss`), not loaded from Google Fonts, 2026-08-03.** Google Fonts cost two chained cross-origin requests on every page load — fetch CSS from `fonts.googleapis.com`, which points at font files on `fonts.gstatic.com`, a second origin with its own connection-setup cost, not loadable in parallel with the first. Self-hosting removes both; the font-face rules are just more of the CSS the browser already fetches. **Only the `latin`/`latin-ext` Unicode-range subsets were downloaded** (not Google's other 5: cyrillic, cyrillic-ext, greek, greek-ext, vietnamese) — this site has no content in those scripts, so shipping them would be pure waste. To fetch the full set (e.g. if non-Latin content is ever added), request `https://fonts.googleapis.com/css2?family=Fira+Sans:wght@400;500;600;700&display=swap` with a real Chrome User-Agent string (a generic one gets served the much-larger legacy `.ttf` format instead of `.woff2` — Google's content negotiation keys off recognizing the UA specifically, confirmed by testing both) and add the missing subsets' files + `@font-face` rules.
- **Frontend interactivity:** Vanilla JS only, inlined in `<script>` tags inside the relevant `_includes/*.html` file (no bundler, no framework, no shared JS file). Each interactive section owns its own script block.
- **Content automation:** Node.js scripts in `.github/scripts/` call the Gemini API (`@google/genai`) and the Unsplash/YouTube Data APIs, run on a schedule via GitHub Actions, and commit their output straight into `_data/*.json`. The Jekyll templates then read those JSON files at build time — there is no runtime API calls from the browser for AI content.
- **`<title>`/meta description always fall back to `user.login`/a static string, never render blank (2026-08-03).** `header.html`'s `page_title`/`meta_description` (non-post pages) come from `site.github.owner.name`/`.bio` via the `jekyll-github-metadata` plugin — both source from GitHub profile fields that are optional and were blank, so the live site was shipping an empty `<title>` and empty meta description (caught by PageSpeed Insights' SEO audit). `page_title` falls back to `user.login` (the GitHub username, always present); `meta_description` falls back to a static one-line site description if `user.bio` is blank. **If adding a new page/template that sets its own title/description, don't assume `user.name`/`user.bio` are populated — use the same `| default:` pattern or an explicit fallback.**
- **No cache-busting on `header.html`/`footer.html` asset URLs (`styles.css`, and the 4 shared scripts loaded from `footer.html`), removed deliberately 2026-08-02.** A cache-busting query string was tried twice this same day and reverted both times:
  - **First**: `?v={{ site.time | date: '%s' }}` (Jekyll's build timestamp) — added after a real phone showed completely unstyled markup for a just-shipped feature while DevTools' phone emulation looked correct, root-caused to the browser serving a stale cached `styles.css` indefinitely (no signal to ever re-fetch it once the URL never changes).
  - **Second**: `?v={{ site.asset_version }}` (a manually-bumped integer in `_config.yml`) — because `site.time` changes on *every* build, including bot commits to `_data/*.json` that never touch `styles.css`/the JS files, and `styles.css`'s `<link>` blocks execution of subsequent scripts on the page when uncached — so every unrelated deploy was forcing a real, visible delay on the next visitor's load, not just extra bandwidth. This surfaced as a bug: `youtube_feed.html`'s inline script got delayed just long enough after a deploy for its static HTML placeholders to flash on screen before being replaced with real data.
  - **Explicit user decision: remove cache-busting entirely rather than keep tuning it.** Trade-off accepted knowingly — a future CSS/JS change may not reach a returning visitor's browser until they hard-refresh or their cache naturally expires, the same failure mode that motivated adding this in the first place. If that bug resurfaces, the fix history above (this section) is the context for whichever approach gets tried next — don't re-add `site.time`-based busting blind, it was already found to have a real cost, not just an accepted "negligible" one.

**Page Composition (`_layouts/home.html`):**
Two mutually exclusive layouts controlled by `site.layout` in `_config.yml` (`stacked` vs sidebar), both rendering the same includes in the same order:
1. `masthead.html` (bio/avatar — the "About" section)
2. `gratitude.html`
3. `youtube_feed.html` ("Reclaiming the Algo")
4. `thoughts.html` ("Insights & Writing" — Medium feed + `learning_board.html` trivia side-by-side)
5. `photography.html`
6. `projects.html` / `interests.html` are present but wrapped in `{% comment %}` — currently disabled, not deleted.
7. `floating_toc.html` renders last but is `position: fixed`, so it overlays regardless of DOM order.

`floating_toc.html`'s anchor list is the single source of truth for actual page order — if you reorder sections in `home.html`, update the TOC's `data-target` list and anchor IDs to match, or the nav will silently point at the wrong section.

**Data Flow / Automation Architecture:**
```
.github/workflows/*.yml (cron)
        │
        ▼
.github/scripts/*.js (Node, Gemini/Unsplash/YouTube APIs)
        │
        ▼
_data/*.json  (committed back to the repo by the workflow itself)
        │
        ▼
_includes/*.html  (Liquid reads _data.* at Jekyll build time, renders static HTML)
```
Each dynamic section has its own workflow → script → JSON file → include, all four wired 1:1:

| Section | Workflow | Script | Data file(s) |
|---|---|---|---|
| Gratitude | `ai-gratitude.yml` | `generate_gratitude.js` | `_data/gratitude.json` |
| AI Trivia (`learning_board.html`) | `ai-learning.yml` | `generate_learning.js` | `_data/learning.json` |
| YouTube Feed | `ai-youtube.yml` | `fetch_youtube.js` | `_data/youtube.json`, `_data/youtube_eval_log.json` |
| Unsplash Gallery | `unsplash.yml` (standalone, own schedule) | `fetch_unsplash.js` | `_data/unsplash_all.json` (entire profile, paginated), `_data/unsplash_favourites.json`, `_data/unsplash_meta.json` (change-detection cache — see below), `assets/photography/<id>.jpg` (downloaded image bytes — see below) |
| Medium Articles (`thoughts.html`) | `medium.yml` (standalone, own schedule) | `fetch_medium.js` | `_data/medium.json` |

`ai-daily-content.yml` is the orchestrator: it runs daily (`30 0 * * *` UTC) and calls the youtube/gratitude/learning child workflows via `uses:`/`secrets: inherit`, but each child workflow also has its own `workflow_dispatch` so it can be triggered individually. `unsplash.yml`/`medium.yml` are NOT part of the orchestrator — they run standalone (`unsplash.yml` twice a day at `0 0,12 * * *`, `medium.yml` once a day at `0 1 * * *`).

**Medium articles moved from a live client-side fetch to build-time, 2026-08-03.** `thoughts.html` used to call `api.rss2json.com` directly from the browser on every page view — PageSpeed Insights' network dependency chain showed this taking 834ms and sitting directly on the critical path for every single visitor. `fetch_medium.js` now makes that same call once a day instead, saving the response straight into `_data/medium.json` (same `rss2json` API, just called from a GitHub Action instead of a browser — no new external dependency introduced). `thoughts.html` reads `{{ site.data.medium | jsonify }}` the same way `youtube_feed.html`/`learning_board.html` already read their own build-time data, instead of `fetch()`-ing anything. No change-detection needed here (unlike `fetch_unsplash.js`) — a single small `rss2json` call is already cheap, so there's nothing expensive to gate.

**Change-detection before fetching (Unsplash only, 2026-07-27, extended 2026-08-02):** `fetch_unsplash.js` checks 3 cheap signals before doing the expensive paginated fetch, comparing all of them against `_data/unsplash_meta.json` from the last run — if every one is unchanged, it skips the fetch entirely and exits. This exists because the script runs on a *fixed schedule* regardless of whether the profile actually changed, and fetching the *entire* photo history (see below) on every run, twice a day, whether or not anything's different, would burn meaningfully more of Unsplash's 50 req/hr free-tier budget than the old fixed-size (12/5/12 photo) fetches did.
- `total_photos` on the user profile and the Favourites collection (2 single-object API calls) — catches pure additions or deletions.
- **The single most recent photo's `id`** (a 1-item `order_by=latest` fetch — still cheap, not the full pagination) — added after the user pointed out a real gap: `total_photos` alone misses a delete-one-then-upload-one edit, since the net count is identical before and after even though the actual photo set changed. A freshly reuploaded photo becomes a *different* "latest" photo regardless of whether the count moved, so checking its `id` catches that case too.
- **Known remaining gap, not addressed:** a metadata-only edit to an older, non-latest photo (no add/remove, no new upload) changes neither signal. Catching that would require fetching enough to compare every photo's own `updated_at`, which defeats the point of a cheap pre-check — left as a real but low-priority gap, not silently assumed-covered.
- If another data source is ever changed to fetch "everything" instead of a bounded slice, consider the same layered pattern: a cheap count/identity check first (more than one signal if a single count can miss same-size replacements), a persisted "last known state" file, skip the expensive call only when *all* signals agree nothing changed.

**Photos are downloaded into the repo, not hotlinked from Unsplash's CDN (2026-08-02):** `fetch_unsplash.js`'s `syncLocalImages()` runs after both paginated fetches complete (so only on the full-fetch path, not the change-detection short-circuit above — if nothing changed on Unsplash's side, the local files from the last sync are still accurate) and downloads every photo's `urls.small` (deduped by `id` across `unsplash_all.json` + `unsplash_favourites.json`) into `assets/photography/<id>.jpg`, skipping any `id` that already has a local file. It also deletes any local `.jpg` whose `id` is no longer in the current fetch — the "crosscheck if they're still on the profile" half. `photography.html`'s `rawPhotos` points its `url` field at this local path (`/assets/photography/<id>.jpg` via `relative_url`) instead of `photo.urls.small` directly; `links.html` (the click-through target) still points at the real Unsplash page regardless.
- **Why:** a visitor's browser was fetching Unsplash-hosted image bytes live, on every view, subject to Unsplash's own CDN response time — outside this site's control and a real source of slow-feeling page loads. Serving from GitHub Pages instead puts photo delivery on the same fast path as every other asset on the site. Unsplash's license explicitly permits downloading and redistributing photos, so this is legally fine, not just technically convenient.
- **Trade-off accepted:** repo size grows with the photo count (~45 photos at Unsplash's "small" size is a few MB) and doesn't shrink back down in git history when a photo is later removed from the profile — accepted as reasonable for a personal site at this scale; revisit (e.g. periodic history rewrite, or an LFS/external-bucket approach) only if this becomes a real problem, not preemptively.
- **`fm=jpg` is forced on the download URL** (not the URL stored in `_data/unsplash_all.json`, which is left untouched) — Unsplash's CDN can serve WebP/AVIF depending on content negotiation, and since the local file is saved with a `.jpg` extension and GitHub Pages serves `Content-Type` by extension, a mismatched actual format would be technically wrong even if most browsers tolerate it via sniffing.
- **First-run migration guard:** `unsplash_meta.json` already existed from before this feature shipped, so on the very first run afterward, the cheap change-detection signals would legitimately all match (nothing changed on Unsplash's side) even though `assets/photography/` had never been populated — `fetch_unsplash.js` also checks `hasLocalPhotos` (does the directory exist and have at least one `.jpg`) before treating a run as "unchanged, skip," specifically to force that first sync through regardless of whether the cheap signals moved.
- **`unsplash.yml` stages deletions too:** `git add -A -- assets/photography`, not a plain `git add`, since `syncLocalImages()` can remove files as well as add them — a plain `git add <path>` only stages additions/modifications, not files deleted from disk.

**Design System Rules:**
- The single source of truth for colors, typography, spacing, radius/shadow scale, and component patterns is [DESIGN.md](../DESIGN.md). Always check it before hardcoding a new color or picking a new radius/shadow value — reuse what's there instead of introducing a slightly different one.
- **Dark mode is a real runtime toggle**, not a build-time-only setting — a `data-theme="light"|"dark"` attribute on `<html>` (set from `_config.yml`'s `site.style` at build time via Liquid in `header.html`, overridable at runtime by the Rectangle toggle button in `floating_toc.html`, persisted to `localStorage`). Colors are a CSS custom-property layer (`--fg`, `--surface`, `--border`, `--accent`, etc.) defined as **two** blocks in `assets/styles.scss` — `:root { }` (light defaults) and `[data-theme="dark"] { }` (overrides) — both shipped to the browser on every load, switched instantly by the attribute, no rebuild needed. There are **no** `{% if site.style == 'dark' %}` branches left anywhere in the codebase (not for colors, not for Primer class toggles) — every one was converted to `var(--token-name)` or one of the `.theme-fg`/`.theme-fg-muted`/`.theme-surface`/`.theme-surface-page`/`.theme-border` utility classes, specifically so the whole page actually responds when the toggle is clicked. If you add new themed CSS, add the value to **both** blocks (or reuse an existing token) — never reintroduce a Liquid `{% if site.style == 'dark' %}` branch for color; that mechanism is gone.
- Spacing is Primer utility classes (`p-4`, `mb-5`, `d-flex`, etc.) plus ad-hoc inline `style="..."` for anything Primer doesn't cover.
- Collapsible sections use native `<details open>` + `<summary>` with a bouncy open/close animation — see the Interaction Rules entry below, this is no longer zero-JS.

**Interaction Rules:**
- Each `_includes/*.html` file is self-contained: its own `<script>` and `<style>` blocks at the bottom of the file. Do not centralize JS into a shared `main.js` — the existing convention is one file per feature.
  - **Four deliberate exceptions**, all loaded site-wide via `_includes/footer.html`: `assets/js/accordion.js` drives the bounce open/close animation for every `details.animated-details` on the page (a cross-cutting UI primitive used by 4 sections, not a single feature); `assets/js/quote-typing.js` types out every `<blockquote>` on the page on first scroll-into-view, for the same reason — a generic rule, not a one-off; `assets/js/aurora-reveal.js` runs the on-load reveal sweep for every `.aurora-text` element (currently 2 usages in `masthead.html`); `assets/js/accordion-grouping.js` joins adjacent closed `.js-accordion-group` sections into a flush block (currently one group of 3, the homepage's main sections) — same justification, a generic rule operating on whatever elements carry that class, not hardcoded to specific sections. See [DESIGN.md](../DESIGN.md)'s Motion/Component Patterns sections for the easing/timing values and the markup assumptions each script makes. Don't flag any of these as a convention violation; don't add a fifth shared JS file without the same cross-cutting justification.
- Scope `document.getElementById`/`querySelector` calls to IDs/classes that are unique to that include; several sections already coordinate via small global hooks on purpose (e.g. `window.filterTrivia`, `window.currentTypingTimeout` in gratitude's typewriter circuit breaker) — check `thoughts.html` and `gratitude.html` before adding another one so hooks don't collide.
- `_data/*.json` files are written by GitHub Actions, not by hand — editing them locally is fine for testing but will be overwritten on the next scheduled run.
